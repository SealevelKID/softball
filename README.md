# 慢壘賽程資訊系統 - 開發筆記與技術覆盤

---

### 💡 系統開發與使用者痛點分析 (Development Background & Pain Points)

* **告別痛苦的看圖與翻表**：以前每到春秋聯賽，主辦單位提供的 Excel 檔手機不易閱讀，賽程圖放大就糊掉。想看自己的隊伍得一張張用肉眼找，非常耗時。


* **打破地區資訊孤島**：雙北各區（如三重、新莊、樹林、五股等）的賽事資訊各自為政。對於會跨區打比賽的球隊來說，無法一次看清全部的賽程。


* **輕量化平台誕生**：為了解決這些麻煩，決定自己動手做一個專為慢壘球友設計的輕量化賽程查詢與統計平台。



---

### 🛠️ 資料清洗與非同步 API 串接策略 (Data Cleansing & API Integration Strategies)

* **圖片切塊餵 AI 辨識**：一開始直接把大圖丟給 AI 辨識，結果很容易漏字跟判斷失準。後來寫了個小程式把大圖切成小圖後再餵給 AI，準確率就大幅提升了。


* **API 限流與配額管理**：因為一次讀取太多張圖會撞到 API 的流量限制，所以學會了切換第二組 Key 來做備援。


* **確定性優先於非確定性判斷**：原本放給 AI 去自由判斷主客隊，結果每次吐出來的位置都在飄移錯亂。最後決定放棄讓 AI 猜，改成嚴格遵循原始表格「左/右」的物理位置來解析，資料才終於穩下來。



---

### 📊 實體對齊 (Entity Resolution) 與異常數據過濾 (Anomaly Data Filtering)

* **解決同隊不同名**：同一支隊伍在不同球場或分組，常常會出現簡稱或打錯字的情況，人工核對起來快崩潰。後來想到拿歷史參賽名單與跨區資料來互相交叉對照（cross-check），半自動地救回了六成以上的隊伍名稱。


* **從「除錯工具」延伸出核心功能**：起初做「隊伍場數統計」只是想抓 bug，看看哪一隊的場次數量異常，藉此反查是不是名字打錯或 AI 辨識失敗。沒想到這個統計表出乎意料地好用，乾脆把它變成入口選單，點一下隊名就能直接跳轉看「單隊賽程」或是「跨區總賽程」。



---

### 📱 行動優先 (Mobile-First) 介面設計與 UX 最佳化

* **跨裝置適配體悟**：網頁在電腦螢幕上看起來很完美，結果放到手機實測才驚覺按鈕太小、字體太擠，根本不好按。


* **專屬目標族群的極簡設計**：考量到打慢壘的球友年齡層分佈，版面使用粗體字、直覺資訊以及好點擊的按鈕，以簡單實用為主。



---

### ☁️ Serverless 架構應用：基於 GAS 的動態狀態同步 (Serverless & Real-time Sync)

* **用 Google 試算表當無腦後台**：比賽每週要更新(完賽或延賽)，如果每次都要改 code 再重新部署到 GitHub 實在太麻煩了。


* **免重新部署的即時賽況**：利用 Google Apps Script (GAS) 把 Google Sheet 變成 Web API。現在管理員只要在手機上打開試算表，用下拉選單改一下狀態，網站前端就會非同步拉取最新賽況，即時同步。


* **背景日誌紀錄**：延續以前專案的經驗，把「使用者下載截圖」的日誌改成非同步在背景發送，完全不會卡住或影響使用者存圖片的順暢度。



---

### 🐛 邊界條件 (Edge Cases) 踩坑與 Regex 除錯紀錄 (Debugging Log)

* **離奇失蹤的隊伍**：在看統計名單時，發現實體隊伍「康德科技長春」沒有顯示出來。


* **字串比對的誤殺陷阱**：原本是為了過濾掉 `長春1`、`長春.1/4(勝)` 這種晉級代號，所以把「長春」兩個字放進了排除名單。結果因為單純用字串包含（includes）來比對，直接把整支真實球隊也當成代號誤殺了。


* **精準的正規表達式 (Regex)**：後來將過濾條件改成精準的正則表達式 `^長春[\d\.]`，嚴格限定必須是「長春開頭，且緊接著數字或點號」才排除，終於順利放行了真實球隊。



---

### 🚀 產品迭代思維與開發總結 (Iteration Mindset & Conclusion)

從一開始單純只想解決自己看賽程的麻煩，到後來一路串接 AI 辨識、跨區名單統整、手機版面調校，再到搞定試算表後台。整個過程讓我深刻體會到軟體開發的真諦：「先把東西做出來跑通，再從實際使用的痛點一步步迭代優化」，這個過程真的充滿了成就感與樂趣。
